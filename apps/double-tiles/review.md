# Double Tiles — 검증 보고서 (review.md)

검증일: 2026-11-25 · 검증자: Review 서브에이전트 · 기준: `apps/double-tiles/spec.md`

## 1. 요약

- **통과 31 / 실패 0 / 미검증 3** (spec 8절, 34항목)
- 최종 판정: **통과(조건부)**. 로직·UI·저장·접근성 모두 기대대로 동작한다. 검증 중 찾은 알림 관련 버그 2건은 `ui.js`에서 고쳤고 다시 확인했다. 미검증 3건은 실제 터치 제스처, `prefers-reduced-motion` 에뮬레이션, 진짜 sandbox iframe으로, 도구 한계 때문에 확인하지 못했다(코드상 대응은 있음).
- 검증 방법: 5개 파일 코드 리뷰, Node에서 `game.js`를 `file:///`로 import해 32개 단언 실행(모두 통과), 내장 브라우저(`http://localhost:8000/apps/double-tiles/`)에서 375px·라이트/다크·iframe 테스트.

Build 에이전트 설명 확인 결과:
- 배경 칸 16개 HTML 고정: 사실(`index.html` 39–44줄, DOM에서 `.cell` 16개 확인). spec 6.1 허용 범위.
- 마우스 드래그 스와이프 허용: 사실(`ui.js` `onPointerDown`이 pointerType을 거르지 않음). spec 5.2에서 선택 사항으로 허용.
- 단계 달성 알림 "<새 단계>단계 달성! 다음 목표 <새 목표>": 사실. 64 달성 시 "2단계 달성! 다음 목표 128"(spec 6.4 예시와 같음). spec 2.1의 예시 "3단계 달성! 다음 목표 512"와는 번호 체계가 다르다. spec 안의 두 예시가 서로 맞지 않으므로 실패로 보지 않고 4절에 적었다.
- 저장된 stage/target이 잘못되면 버리지 않고 maxTile로 다시 계산: 사실(`game.js` 221–228줄). spec 7절의 "버리는" 조건(size, grid, score)에는 stage/target이 없으므로 위반은 아니다. 다만 아래 4절 참고.

## 3. 발견한 문제와 수정 내용

### 3.1 한 이동에서 단계 달성과 게임 오버가 겹치면 단계 알림이 사라짐
- 위치: `ui.js` `announceGameOver` (수정 전 181–186줄)
- 원인: `handleMove`가 `pendingStage`를 채운 뒤 게임 오버면 `announceGameOver`가 타이머를 지우고 `pendingStage`를 비워, 단계 달성 알림이 나가지 않았다(spec 8.4 "단계 달성이 aria-live로 알려진다").
- 조치: 게임 오버 알림 전에 남아 있는 단계 알림을 `#sr-status`에 바로 쓴다. 게임 오버 문구(`#sr-alert`)는 spec 6.4 그대로 둔다.
- 재검증: 32+32 → 64를 만들며 게임 오버가 되는 격자 주입 → `#sr-status` "2단계 달성! 다음 목표 128", `#sr-alert` "게임 오버. 최종 점수 64, 2단계". 통과.

### 3.2 새 게임 뒤에 이전 판의 점수 알림이 늦게 나감
- 위치: `ui.js` `startNewGame` (수정 전 210–218줄)
- 원인: 점수가 오른 이동 직후 400ms 안에 "새 게임"을 누르면 디바운스 타이머가 남아 있어 이전 판의 "점수 N, M 획득"이 새 판에서 읽혔다.
- 조치: `cancelStatus()`(타이머와 대기 알림 비우기)를 추가하고 `startNewGame`에서 호출.
- 재검증: 점수가 오르는 이동 직후 새 게임 → 600ms 뒤 `#sr-status` 빈 문자열, 점수 0. 통과.

## 4. 남은 문제·미검증 항목

- **미검증 3건**: 실제 터치 제스처의 스크롤/새로고침 방지, `prefers-reduced-motion` 실제 동작, 진짜 `sandbox` iframe. 모두 코드에는 대응이 있다. 실제 모바일 기기나 개발자 도구(Rendering 탭 reduced-motion 에뮬레이션)로 한 번 확인하기를 권한다.
- **spec 안의 단계 알림 예시가 서로 다름**(수정하지 않음): 2.1절 "3단계 달성! 다음 목표 512"와 6.4절 "2단계 달성! 다음 목표 128". 구현은 6.4 방식(새 단계 번호)이다. 2.1 방식이라면 512가 4단계 목표라 번호가 하나 어긋난다. spec을 어느 쪽으로 맞출지 사용자 확인이 필요하다.
- **저장된 stage/target의 일관성 검사가 약함**(낮음, 수정하지 않음): `stage: 1, target: 4096`처럼 서로 맞지 않는 값도 받아들인다. spec 7절의 버리는 조건에는 없으므로 위반은 아니다. 손으로 고친 저장값에서만 생긴다.
- **로컬 서버와 sandbox iframe**(참고): `allow-same-origin` 없는 sandbox iframe은 출처가 opaque라 ES 모듈을 CORS로 받는다. `serve.mjs`는 `Access-Control-Allow-Origin`을 보내지 않으므로 로컬에서는 그런 iframe에서 스크립트가 안 뜰 수 있다. GitHub Pages는 이 헤더를 보내므로 배포 환경과는 다를 수 있다. 블로그 파일이라 수정하지 않았다.
- **테스트로 인한 저장값 변화**: 테스트 초기에 `localStorage`를 비웠고 상태를 주입해, 이 브라우저의 `double-tiles:best`가 테스트 값(1,240)으로 바뀌어 있다. 실제 플레이 기록과 섞이지 않게 하려면 개발자 도구에서 `double-tiles:best`를 지우면 된다. 진행 중 저장은 마지막에 새 게임으로 초기화했다.
